# Slice relief: make the planet look like a photograph, not a polygon

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ridge shadows, crisp coastlines and slope-aware colour **at orbital distance**, without loading orbital-scale terrain geometry.

**Architecture:** A second provider alongside the terrain one — a custom Cesium `ImageryProvider` that generates a shaded-relief, slope-coloured raster per tile from the same WASM engine, in the same worker pool. **The engine is not touched.** No new exports; `wb_fill_tile_f32` already returns a height grid.

**Spec:** No spec section governs appearance. This slice is owner-requested, and its acceptance is visual — so it is measured against a stated reference rather than a number.

## The measurement that motivates it

At the default orbital view — camera at **12,674 km** — the globe renders **16 tiles at levels 1 and 2**. Post spacing at those levels is **156.4 km and 78.2 km**. Every coastline in a whole-planet screenshot is a polygon through points **78 km apart**.

That is the entire cause of the "low-poly" look. It is a *resolution* problem, not a shading one, and the appearance work already committed (lighting, sky limb, a ramp with depth and snow bands) does not touch it.

**Brute force is not the answer, and this is why.** Reaching ~1 km detail across a visible hemisphere means level 7-8 terrain. Cesium would need thousands of *meshes* at orbital view instead of sixteen. The cost is not in generating heights — it is in building, uploading and drawing that many tile geometries.

## RESEARCH, added after this plan was written, and it strengthens the case

Three findings from a survey of shipped planet renderers and the CesiumJS source.

### 1. This is not merely the best way to get relief shading. It is the ONLY way.

**`CustomHeightmapTerrainProvider` has `hasVertexNormals = false`, always.** `HeightmapTerrainData` has no
normals path anywhere in Cesium; vertex normals exist only as oct-encoded normals on
`QuantizedMeshTerrainData`. So `GlobeFS` falls back from `ENABLE_VERTEX_LIGHTING` to
`czm_geodeticSurfaceNormal` — **the ellipsoid normal.**

**Verified on the running viewer: `hasVertexNormals: false`.** The mountains are lit as though the planet
were a perfect smooth sphere. Turning `enableLighting` on, as this project did, changed nothing, because
there is no terrain normal for it to use.

It also silently breaks `SlopeRamp` and `AspectRamp`, which read `czm_octDecode(encodedNormal)`.
`ElevationRamp` works because `v_height` comes straight off vertex position — which is exactly why the
current picture is colour-by-height and nothing else.

### 2. Two shipped engines do exactly this, and say so

**Outerra**, on how its terrain reads as detailed: *"the normal maps are generated from finer fractal
subdivision"* than the mesh. That is this plan's whole technique in one sentence, from an engine whose
public claim is centimetre-scale detail on a whole planet.

**Flavien Brebion (Infinity)**: *"The most details of a landscape comes from lighting variations generated by
the normal map rather than geometry"* — a 128×128 normal map over 64×64 geometry *"would look similar from
above and slightly worse from ground level."*

**Frontier (Elite Dangerous)**: above a certain LOD, *"flat geometry is used with textures generated for the
look, normals, and height of the terrain"*, switching to real geometry only near the ground.

Three independent engines converged on shading at a higher frequency than tessellation. **Treat it as
established practice rather than an idea to validate.**

One honesty note: no graphics paper appears to quantify "shading dominates terrain shape perception". The
nearest rigorous evidence is cartographic — the **terrain reversal effect** (Biland & Çöltekin 2019), where
illuminating from the lower-right makes mountains read as valleys **with no change to the elevation model at
all.** That is an illusion study, not a detail-budget study. The practice is well-supported; the perceptual
claim is not measured.

### 3. Cesium hands us a 4× colour resolution win for free

Imagery level is chosen by `getLevelWithMaximumTexelSpacing` against
`errorRatio × terrainProvider.getLevelMaximumGeometricError(tile.level)`, clamped only to the **provider's**
min/max — **there is no clamping to the terrain tile's level.** `errorRatio` is hardcoded `1.0`, with a
revealing comment in the source: *"should really be imagerySSE / terrainSSE… but first we need configurable
imagery SSE."*

Worked through for a 256 px geographic provider, Cesium picks **imagery level == terrain level**: one imagery
tile per terrain tile, but **256 texels across a rectangle the geometry samples with only 65 posts.**

**We currently run no imagery at all** (`baseLayer: false`). So this is a ~4× sharper picture from the same
tiles — and more importantly, an imagery tile is a raster sampled from the **true field**, whereas
`Globe.material` only ever sees values interpolated across 78 km posts.

**Known trap:** forcing imagery finer via `imageryProvider.minimumLevel` produces "too many tiles at the
minimum level" errors and blows past texture-unit limits. Do not reach for it.

### And the measured arithmetic behind the 78 km figure

```
levelZeroError = R·2π·heightmapTerrainQuality / (tileImageWidth · nTilesAtLevel0)
               = 6378137·2π·0.25 / (65·2) = 77,067 m
levelL error   = 77067 / 2^L
```

Level 1 gives 156 km posts, level 2 gives 78 km, and at ~1.3×10⁷ m the level-2 SSE lands near 1.1-1.5 against
a threshold of 2, so refinement stops. **The measurement in this plan is predicted exactly by the defaults.
Nothing is broken.**

## The idea: shade at a different frequency than you tessellate

Keep the mesh coarse. It only has to hold the silhouette and the horizon. Generate a **raster** per tile at much higher frequency than the mesh, from the same height function, and let per-pixel shading carry the detail.

A 256×256 raster is far cheaper than a 256×256 mesh, and it is the technique behind every "photo from space" planet render. The heights come from `wb_fill_tile_f32`, which already exists and is already exercised by the terrain path.

**Three things the raster can do that a `Material.ElevationRamp` cannot**, and they are the whole visual gap:

1. **Hillshade.** A sun direction against the local surface normal. This is what makes a mountain range read as a mountain range.
2. **Slope-aware colour.** Rock on steep faces, green on flat ground, *at the same elevation*. A height ramp physically cannot do this — it is given height and nothing else.
3. **Detail below the mesh.** The raster can sample at level `n + 3` while the mesh stays at level `n`.

## What this slice must NOT do

- **No engine changes.** No new `#[no_mangle]` exports, no changes to `wb_fill_tile_f32`, no changes to any Rust source. If a task believes it needs one, stop and say so — that would move this out of viewer-only scope and into the conformance-gated tree.
- **No network.** The CSP is `default-src 'self'` with no `'unsafe-inline'`, and the viewer's whole claim is that it runs offline. Nothing is fetched, no CDN, no texture download.
- **No replacement of the terrain provider.** The relief layer sits *alongside* it. `?paint=0` and `?flat=1` must still produce exactly what they produce today.
- **No clouds.** Worth doing, cheap, and a separate thing — it is decoration over this, not part of it.

## Global Constraints

- **The viewer is not fingerprinted**, so nothing here moves the source digest and no re-bless is needed. **Confirm that with `npm run check:wasm` rather than assuming it**, because a task that strays into `crates/` will move it.
- **`verify.js` asserts nothing about appearance** — checked, no hits for lighting, atmosphere, material, ramp, or fog. It does assert plenty about tiles and workers. **Do not break those**; run the harness.
- **A green build can contain nothing.** This project shipped a 327-byte WASM module exporting only `memory`. The equivalent failure here is a provider that returns blank rasters and looks like "the layer is subtle". **Assert non-blankness**, and prove the assertion can fail.
- **`f64::min`/`max`/`clamp` are banned in Rust** — not applicable to JavaScript, but the NaN discipline is: a slope of `NaN` must not silently shade as flat.
- **`worldbuilder/` must not be modified.** `worldbuilder/integration/maritime.py` has a pre-existing uncommitted change; leave it unstaged. **Never `git commit -a`.**
- **`fixtures/dragonsire/` is a gitignored real game database.** It must never appear in a commit.
- **Every figure names its population, its method with parameters, and its host.** Frame timings are figures.
